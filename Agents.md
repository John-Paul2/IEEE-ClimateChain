# VeriCEMS: workspace rules (read before every task)

## What this project is
VeriCEMS is a hackathon prototype (IEEE ClimateChain Hackathon 2026, Track 4). It makes industrial stack-emissions data tamper-evident for EU CBAM: signed, hash-chained telemetry; physics and ML checks; a bonded 3-of-5 verifier quorum with a challenge window on an EVM testnet; and an importer portal with a CBAM cost calculator.
Source of truth for design and scope: docs/VeriCEMS_Project_Guide.md. Shared formats: docs/INTERFACES.md (once it exists). If they disagree, stop and ask me.

## Scope freeze
Build only the must-have tier in the guide (Sections 1.3 and 13). Do NOT build: zero-knowledge circuits, live satellite integration, a Scope 2 / precursor engine, or physical hardware. Never add features that the current prompt did not ask for. Put good ideas in docs/FUTURE_WORK.md instead.

## Honesty rules (highest priority)
1. Never invent numbers, results, citations, regulation values or links. Every number in the UI or docs must come from (a) a results file generated by code in this repo, (b) a config value with a source and a last_verified date, or (c) be tagged [ILLUSTRATIVE].
2. If an experiment gives a poor result, report it as it is. Never tune labels, thresholds or splits on test data to look better.
3. Anything simulated must be labelled "synthetic" in code (names), data cards, UI and docs. Real data means US EPA CAMPD only.
4. Regulatory values (benchmarks, default values, CSCF, factors, prices) are inputs in config files. If unknown, store null and make the UI show "needs source". Never guess them.
5. Say "CBAM-aligned", never "official". Say "informed by" for standards, never "compliant". Never claim zero-knowledge, hardware security or any feature that is not actually built.
6. If real data cannot be obtained or something cannot be run, stop and tell me. Do not substitute fake data into reported results. Synthetic fixtures are allowed only inside unit tests and must be named as such.

## Engineering rules
- Monorepo: contracts/ backend/ ml/ web/ calculator/ docs/ data/ scripts/ results/ deployments/ config/.
- Python 3.11+ in a virtualenv (.venv); Node 20+; Foundry for contracts. Pin versions (lock files, foundry.toml).
- Determinism: fixed seeds, pinned libraries, CPU-only inference, scores quantized to integer basis points (0..10000), canonical JSON (sorted keys, no whitespace) for hashing.
- Every module has tests. Run them before saying a task is done, and include the real command output in your report.
- Small commits after each green milestone with clear messages. Never rewrite history. Never commit .env, keys, keystores, or data files larger than 5 MB.
- Python: type hints. TypeScript: strict mode. Solidity: NatSpec on public functions, custom errors, no upgradeable proxies.
- Keep dependencies minimal and maintained.
- Directory ownership: when working in one area, do not edit another area unless fixing an interface bug, and say so in the report.

## Security and safety (Turbo mode is on)
- Testnet and local anvil only. Never use a mainnet RPC. Never ask for, read or print private keys.
- No sudo, no global installs, no curl-pipe-shell, no force-push, no deleting outside the workspace. Install into .venv or node_modules only.
- Ask me before any command that deletes more than a build or cache folder.
- Do not read files outside the workspace unless I ask.
- If a command needs a network domain you did not expect, explain why before running it.

## Reporting
At the end of every task, produce a Walkthrough: what changed, commands run with real output, test results, screenshots for UI work, known gaps, assumptions and open questions. Do not say "done" unless the tests pass.

## Style
Readable code, descriptive names, no clever tricks. UI: dark theme using the design tokens in the guide (Section 11.3). Never rely on colour alone. Every panel has loading, empty and error states.
